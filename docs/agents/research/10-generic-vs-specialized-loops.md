# Digest: How specialized should an agent-loop/harness be? (ratchet-overfitting question)

Context read first: `docs/agents/loop-engineering-analysis.md` Parts I §4–5, IV.1, V. The doc already contains half the answer (general detectors vs. grown specific map, earn-your-complexity); this digest tests that position against external literature and fills in the distillation/provenance/storage mechanics it lacks.

## Q1 — Generality vs. specialization of scaffolds: what transfers?

**The recurring empirical pattern: structural/mechanism-level harness elements transfer; content-tuned specifics don't, and actively overfit.**

- **ADAS / Meta Agent Search** (Hu, Lu, Clune, arXiv:2408.08435, ICLR 2025 — https://arxiv.org/abs/2408.08435). Headline claim: agents *discovered* on one domain transfer — math→reading comprehension (+13.6 F1 on DROP), math→held-out math (+25.9% GSM8K), across models. What transferred was **design patterns** (e.g., structured self-critique loops, ensembling), not tuned content. But the replication/critique literature is important for your worry: reviews and follow-ups (VeRO, arXiv:2602.22480; "Rethinking the Value of Multi-Agent Workflow: A Strong Single Agent Baseline," arXiv:2601.12307) find ADAS-style search **overfits its benchmark** — gains are largest exactly where eval sets are small or homogeneous, and when LLM-as-judge is the fitness function the search degenerates into reward hacking. Direct analogue of your ratchet worry: an automated harness-improver optimizing against a fixed check-set overfits that check-set.
- **DSPy/GEPA** (Agrawal et al. 2025, ICLR 2026; production report: Decagon, "Optimizing GEPA for production" — https://decagon.ai/blog/optimizing-gepa-for-production). GEPA beats RL-style optimization with 35× fewer rollouts, **but**: more optimization data made prompts "encode every edge case, producing verbose, over-fitted prompts that failed to generalize" — 20–100 examples consistently beat 500. Cross-model transfer of optimized prompts is positive but degraded (gains highest on the optimizing model). This is the cleanest published demonstration that **an append-only accumulation of case-specific text rules is an overfitting mechanism**, exactly the user's worry — when the rules are *prompt text*.
- **ExpeL** (Zhao et al., AAAI 2024, arXiv:2308.10144 — https://arxiv.org/abs/2308.10144). Insights distilled from experience on HotpotQA **transferred positively to FEVER** (a different task). Notably, *which* memory mode helps is task-dependent: abstract insights helped QA, raw trajectory recall helped ALFWorld, WebShop needed both. So distilled principles do transfer across *related* tasks; episodic specifics transfer only within-task.
- **Voyager** (Wang et al., NeurIPS 2023 workshop, arXiv:2305.16291 — https://voyager.minedojo.org/). The strongest transfer result for *executable* accumulated knowledge: the verified-skill library transferred to **a brand-new Minecraft world** and even to **a different agent** (giving Voyager's skills to AutoGPT raised its success 0/3 → 1–2/3). Skills survive transfer because each was verified against the environment before storage — the analogue of "gates as executable code" transferring better than gates as prose.
- **METR on harness improvements** (elicitation-gap and elicitation-protocol pages — https://evaluations.metr.org/elicitation-gap/, https://evaluations.metr.org/elicitation-protocol/; GPT-4o report — https://metr.org/evaluations/gpt-4o-report/). METR explicitly classifies agent failures into **spurious, fixable with task-agnostic elicitation** (51% of GPT-4o failures) vs. **fixable only with task-specific scaffold modification** (5%). Their protocol deliberately spends effort on task-agnostic fixes and treats task-specific ones as a separate, lower-value category. Practitioner consensus, same direction: **the highest-ROI harness improvements are general**; task-specific patches are a long tail.
- **Bitter-lesson practitioner writing**: "Agentic Harness Archaeology" (av.codes — https://av.codes/blog/agentic-harness-archaeology): "most of what we call an agentic harness is a fossil — the shape a workaround took when an older model could not do something." Hugo Bowne-Anderson ("AI Agent Harness, 3 Principles… and the Bitter Lesson Revisited" — https://hugobowne.substack.com/p/ai-agent-harness-3-principles-for) and MindStudio's harness-maintenance post argue harnesses must be **continually simplified as models improve** — accumulated workarounds are a depreciating asset. This applies to *capability workarounds*, though; it applies much less to *verification gates* (a convergence check is not a workaround for a model deficit — it's a workaround for a simulator deficit, which the model upgrade doesn't fix).
- **SE analogy, confirmed in the literature**: generic linters/types = cheap universal layer; the project-specific test suite is not "bloat" but the **core asset** — "test cases carry constraints learned through real production costs… without the test cases, agents cannot understand why partial results don't count as success" (Johnson Lee, "Test Cases Are Software's Core Asset," Aug 2026 — https://johnsonlee.io/2026/08/30/test-case-is-the-core-asset.en/). Property-based testing is the published "general detectors" middle layer: Anthropic-affiliated "Agentic Property-Based Testing" (arXiv:2510.09907) has agents find real bugs across the Python ecosystem from a *small fixed set of general invariant classes*; "Property-Generated Solver" (arXiv:2506.18315) argues PBT "breaks the cycle of self-deception where tests share flaws with the code they validate" — your generator/verifier-separation point, independently derived.

**Net answer to Q1**: nobody finds that task-tuned harnesses beat general ones *across* tasks; task-tuning wins only on the tuned task and demonstrably overfits (GEPA, ADAS critiques). But task-specific *executable regression checks* are universally treated as an asset, not overfitting — because they're scoped to the artifact they protect and cost nothing when they don't run. The overfitting risk is specific to **task-specific rules stored as always-loaded prose**.

## Q2 — Principle distillation with provenance: closest existing mechanisms

The user's proposal (distill gates→principles, keep episode links for later debugging) has a near-exact classical ancestor and several modern partial implementations:

- **Truth Maintenance Systems** (Doyle 1979; de Kleer's ATMS 1986) — the closest classical match. A TMS stores every derived belief **with its justification structure**: links to the antecedent facts it depends on. When an antecedent is retracted, the TMS automatically identifies and retracts (or re-derives) everything downstream. This is *precisely* "principle annotated with the episodes that motivated it, so its merit can be debugged" — plus the missing piece: **automatic invalidation propagation**. If episode §25 is superseded by §26, every principle justified solely by §25 gets flagged for review, mechanically. Modern survey touchpoint: "Provenance-Based Interpretation of Multi-Agent Information Analysis" (arXiv:2011.04016) describes TMS lineage tracking for exactly this ("recognize contradictions, retrieve logical rationale, identify upstream assumptions").
- **Generative Agents reflection** (Park et al., UIST 2023, arXiv:2304.03442). Reflections are stored **with explicit pointers to the memory records cited as evidence**, and reflections can cite other reflections → a provenance *tree* from abstract principle down to raw episodes. Ablation: removing reflection degenerated agent coherence within 48 simulated hours. This is the direct modern precedent for "distilled principle + episode links."
- **ExpeL insight lifecycle** (arXiv:2308.10144). Insights are maintained by four operations — **ADD, UPVOTE, DOWNVOTE, EDIT** — with an importance counter; an insight repeatedly contradicted by new experience is downvoted and removed at zero. This is the closest thing to a published **merit-debugging lifecycle** for distilled rules. Its weakness relative to the user's proposal: ExpeL does *not* keep episode links, so a downvote can't be traced to its cause. (Caveat: lifecycle details from the paper; the search results confirmed the mechanism exists but not its specifics.)
- **AutoGuide** (Fu et al., NeurIPS 2024, arXiv:2403.08978 — https://arxiv.org/abs/2403.08978). Guidelines are distilled as **conditionals**: "in state S, do/avoid X." Selection by state-matching at runtime means the effective context holds only *applicable* guidelines — the antidote to bloat is not fewer rules but **conditioned rules retrieved by applicability**. Related: **AutoManual** (NeurIPS 2024) — agents build and *update* a rule manual online, revising rules that fail.
- **Memory-consolidation systems** (mechanisms for MERGE / CONTRADICT / provenance): **Mem0** classifies each new fact as ADD/UPDATE/DELETE/NOOP against retrieved neighbors, with `linked_memory_ids` for lineage (https://mem0.ai/blog/memory-in-agents-what-why-and-how); **All-Mem/A-MEM-line** systems merge redundant entries into a "canonical descriptor" while **archiving (not deleting) source evidence, recoverable through lineage links** (arXiv:2603.19595) — merge-with-provenance, exactly the requested shape; Hindsight's consolidation framework names the four levers: importance, merge, decay, eviction (https://hindsight.vectorize.io/blog/2026/05/21/agent-memory-consolidation). Rules for safe merging that recur: merge only what all sources support; never merge conflicting or time-varying facts.
- **Case-based reasoning / case-base maintenance** (Leake & Wilson, "Categorizing case-base maintenance," EWCBR 1998 — https://link.springer.com/chapter/10.1007/BFb0056333). The CBR field spent the 1990s on exactly this lifecycle: when to compile cases into rules, when to keep the cases, how to detect a stale case-base. The hybrid consensus (rule+case systems): **rules carry the general knowledge, cases are retained as the evidence and the exception-handlers** — you keep both, linked. Distill, but never discard the episodes.

**Mechanisms found for the three sub-questions**: MERGING = similarity-threshold + canonical descriptor + lineage links (All-Mem), LLM-classified UPDATE (Mem0). DETECTING a dead principle = (a) TMS-style justification retraction when a motivating episode is superseded; (b) ExpeL-style downvote-on-contradiction; (c) empirical fire-rate tracking (a gate that never fires is a demotion candidate — this one is mostly practitioner CI lore, not a paper). PROVENANCE = Generative-Agents citation pointers; TMS justifications; archive-don't-delete lineage.

## Q3 — Where should accumulated checks live: context vs. code?

The evidence is unusually one-sided:

- **Prompt rules are advisory and degrade superlinearly with count.** Practitioner measurements/consensus around CLAUDE.md: ~80% compliance for prose rules vs. deterministic execution for hooks; past ~60 rules the model "starts ignoring all of them uniformly — every line you add makes every other line less likely to be followed" (TianPan.co, "Your CLAUDE.md Is Probably Too Long" — https://tianpan.co/blog/2026-02-14-writing-effective-agent-instruction-files; dev.to "5 silent failure patterns"). Anthropic's own best-practices doc says keep it lean and **add rules only when they would have prevented a real failure** (https://www.anthropic.com/engineering/claude-code-best-practices) — your earn-your-complexity rule, in official guidance. The emergent maxim: **"CLAUDE.md is for guidance; hooks are for guarantees."**
- **Cost structure**: a prose rule costs tokens + attention on *every* turn whether or not it's relevant, and its marginal cost is paid by *all other rules* (attention dilution). An executable check costs compute only when it runs, zero context, and its reliability doesn't decay as the set grows. This asymmetry is stated repeatedly in the practitioner sources; I found **no quantitative paper** measuring it head-to-head (marked NOT COVERED below).
- **"Compile the lesson into a test" exists as a named pattern**: "Skill Coverage" (arXiv:2606.20659) compiles natural-language skill instructions into **EARS-normalized Skill Behavior Constraints** with applicability conditions, executed by the harness — and explicitly *excludes* rationale/background from compilation (rationale stays in docs; only observable expectations become constraints). Johnson Lee's test-cases-as-core-asset essay is the same argument from the SE side. Voyager (Q1) is the same argument from the agent side: store the *verified executable*, not the prose.
- **A loop-specific extra reason your doc already has**: self-conditioning (Part V) — checks external to the agent's context can't be argued with, drifted past, or marinated in.

**Net**: learned constraints should default to code (gate/test/hook); context gets only (a) the index line pointing at each gate, (b) rules that genuinely can't be executed (judgment calls, style), and (c) the recitation block. This matches your §6.2/IV.3 design and strengthens it.

## Q4 — Hierarchies of generality: layered check-sets

Three fields independently converged on the same three-layer shape:

- **Defense-in-depth guardrail frameworks** (Microsoft Security Blog, "Defense in depth for autonomous AI agents," May 2026 — https://www.microsoft.com/en-us/security/blog/2026/05/14/defense-in-depth-autonomous-ai-agents/; Red Hat, May 2026; Sahu's production framework on Medium): a **domain-agnostic core** (input/tool/output gating, HITL, evals-as-feedback) plus **pluggable domain modules** (banking/healthcare packs) plus per-deployment policies. Cost-tiered: cheap deterministic checks filter first, expensive checks only on survivors — the CI-cascade shape.
- **Safety-case practice** (GSN/CAE traditions; "A Structured Approach to Safety Case Construction for AI Systems," arXiv:2601.22773; GovAI's frontier-AI cyber template — https://www.governance.ai/research-paper/safety-case-template-for-frontier-ai-a-cyber-inability-argument): a **generic argument template** is instantiated with domain hazards and then system-specific evidence. Key transferable idea: the *argument structure* is the reusable layer; the *evidence* is always local. Also: every claim node stays linked to its evidence — safety cases are provenance-annotated principle sets by construction, and they're the most battle-tested such format in engineering.
- **Metamorphic testing taxonomy** (survey arXiv:2406.05397; ML-testing survey arXiv:1906.10742): a small universal vocabulary of MR classes (additive, multiplicative, permutative, invertive, inclusive, exclusive) that transfers across all domains, but deriving *useful* MRs "requires in-depth domain knowledge." One counter-grain finding worth keeping: Murphy et al. found **function-level (more specific) MRs 170% more effective than application-level (more general) ones** — generality of the *class* does not mean the deployed check should be stated generally; the deployed check should be the general class *instantiated as concretely as the artifact allows*.
- **METR's elicitation protocol** (https://evaluations.metr.org/elicitation-protocol/) operationally separates the layers: task-agnostic elicitation is the default budget; task-specific modifications are tracked as a separate category. A working precedent for *accounting* gates by generality layer.

## What this implies for the ratchet design (synthesis + recommendation)

The user's overfitting worry is **correct for exactly one storage medium and wrong for the other two**. Assembled from the evidence:

1. **Keep the ratchet, but make it a compiler with three output targets, chosen at write time.** When a human catch is ratcheted, classify it:
   - **Universal detector** (rare — your ~6–10: convergence, falsifiability, goal-vs-proxy, causal-ablation, orthogonal-modality…). These are the layer that transfers to the next task *by design* (IV.1 already says this; ADAS-pattern-transfer, PBT, and MR-class evidence all confirm the general layer is what survives transfer). Almost never grows.
   - **Domain gate** (contact-sim numerics, controller-regression grids). Transfers across *tasks within this project*, not beyond. Grows slowly.
   - **Task regression check** (this URDF, this choreography). Never transfers — and that's fine, because it lives in CI where non-transfer costs nothing. This is where *most* ratchet output should land, and it is the project's core asset, not bloat (test-suite analogy). Bloat only occurs if these leak into always-loaded context.
   The bloat worry dissolves once you notice the context cost is O(index), not O(gates): 100 task gates in `gates/` + 100 one-line index entries ≈ nothing; 100 prose rules in CLAUDE.md ≈ uniform rule-ignoring (the >60-rules finding).

2. **Adopt the user's distillation proposal — it's a TMS.** Periodic consolidation (your §6.4 pass) should: merge near-duplicate gates into a canonical principle **with lineage links to the merged gates and their motivating episodes** (All-Mem's archive-don't-delete pattern; Generative Agents' citation pointers; safety-case claim→evidence links). The payoff of provenance isn't just debuggability — it enables **automatic staleness propagation**: when an episode is superseded (your §25→§26 case), every principle justified *only* by it gets mechanically flagged. That's Doyle's TMS, 1979, and nothing in the modern agent-memory literature does it better; your first-class supersedable memory (IV.3) is 90% of the way there — add a `justified_by:` field and make the consolidation pass walk it.

3. **Give principles an ExpeL-style empirical lifecycle, not just logical provenance.** Track per-gate: fires/run, catches (fires that changed a verdict), cost. Downvote-toward-archive gates with zero catches over N runs; upvote gates that catch. A distilled principle whose *every* descendant gate has stopped catching is a fossil candidate (bitter-lesson pressure, applied with evidence instead of vibes). Your §II.3 ablation experiment is exactly the right instrument: periodically re-run a known-answer case with a gate removed; if truth still gets reached, the gate's merit is measurably zero.

4. **Condition, don't delete, the mid-generality rules.** For rules that must stay as text (judgment, not executable), use AutoGuide's format: state-conditioned ("when evaluating a contact-rich metric → …") and retrieved by applicability, not always-loaded. A conditional rule that never matches costs one index line.

5. **Expect and accept asymmetric transfer.** When the project moves to the next task (rally game, thrust-vectoring build): carry the universal detectors verbatim, carry domain gates whose domain still applies, and **deliberately leave the task layer behind** (it stays as the old task's regression suite). Do not try to make task gates general at write time — GEPA's overfit-prompts result and the MR-specificity finding both say premature generalization produces worse checks than concrete ones; generality should be *earned at consolidation time* when 2–3 episodes from different tasks justify the same principle (that's the merge trigger, and the provenance links are what let you see the pattern).

**One-line answer to the user**: the ratchet doesn't overfit if (a) its outputs are executable and layered — task-specific gates are a test suite, and test suites are supposed to be task-specific; (b) only the small universal-detector layer and a one-line index ever occupy context; and (c) a provenance-linked consolidation pass (a TMS, essentially) merges, demotes, and retires — so accumulation is append-only in *history* but not in *active surface*.
